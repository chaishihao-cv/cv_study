## 二、为什么需要卷积：MLP 的两个死穴

### 死穴一：参数量随像素数爆炸

MLP 第一层 `Linear(784, 128)`，权重 (128, 784)，**100480 个参数**。

换成 224×224 彩色图：

```text
输入维度 = 3 * 224 * 224 = 150,528
第一层   = 150,528 * 128 + 128 = 19,267,712    约 1927 万参数
```

再换成 1080p：

```text
6,220,800 * 128 + 128 = 796,262,528            约 7.96 亿参数
```

**7.96 亿个 float32 就要 3 GB 显存，还只是第一层。**

### 死穴二：没有空间概念

`flatten` 把 28×28 压成 784 维，**「哪两个像素挨着」这个信息完全丢掉**。

后果：图像整体平移 3 个像素，压平后的向量全变，MLP 认不出来 —— **但人一眼就知道还是同一个数字。**

### 卷积用两招同时解决

| 招 | 做法 | 收益 |
|---|---|---|
| **局部连接** | 每个输出只看 3×3 的一小块 | 连接数从 15 万降到 27 |
| **权重共享** | 同一组核在整张图上滑 | 参数与图像大小无关，天然平移等变 |

**数字对比：**

```text
MLP 第一层（224 彩色）:       19,267,712
Conv2d(3, 64, 3):                     1792
差了 10,752 倍
```

## 三、卷积在算什么（手算核心）

### 输入与核

输入 5×5（带行列编号只为说明「盖在哪」）：

```text
      列1 列2 列3 列4 列5
行1    1   2   3   4   5
行2    6   7   8   9  10
行3   11  12  13  14  15
行4   16  17  18  19  20
行5   21  22  23  24  25
```

卷积核 3×3：

```text
 1   0  -1
 1   0  -1
 1   0  -1
```

### 算左上角：三小步

**第一步：核盖住输入左上角 3×3**

```text
 1   2   3
 6   7   8
11  12  13
```

**第二步：位置对位置相乘**

```text
上排:  1*1 = 1     2*0 = 0     3*(-1) = -3
中排:  6*1 = 6     7*0 = 0     8*(-1) = -8
下排: 11*1 = 11   12*0 = 0    13*(-1) = -13
```

**第三步：9 个乘积全部相加**

```text
1 + 0 - 3 + 6 + 0 - 8 + 11 + 0 - 13 = -6
```

**左上角 = -6。** 这就是一次「乘加」（MAC）：**9 次乘法 + 8 次加法**。

### 更快的看法（推荐用这个）

核的第一列是 1、第三列是 -1、中间一整列是 0，所以它就是：

```text
（输入左列的和） - （输入右列的和）        中间列乘 0，直接跳过
```

左上角那块：

```text
左列: 1 + 6 + 11 = 18
右列: 3 + 8 + 13 = 24
18 - 24 = -6
```

### 为什么 9 个输出全是 -6

输入每一行都是等差数列（相邻差 1），所以「隔一格」的差恒为 2：

```text
每行左列 - 右列 = -2
三行相加 = -2 * 3 = -6
```

**核滑到任何位置，盖的都是完整三行，所以恒等于 -6。** 9 个值相同不是巧合，是可以推出来的。

### 一个重要规矩：不要翻转核

学术定义的「卷积」要把核翻转 180 度。但 **PyTorch 的 `Conv2d` 不做翻转**（数学上叫互相关）。

**所以手算就按「对齐了直接乘」，代码和手算才会一致。**

## 四、输出尺寸公式

```text
out = (in + 2 * padding - kernel) // stride + 1
```

### 三步拆解

```text
第 1 步：分子 = in + 2*padding - kernel      （补零后的总长度里，核能占几格）
第 2 步：分子 // stride                      （能滑几步，// 是向下取整）
第 3 步：+ 1                                 （起点那一格）
```

**必须用 `//` 不能用 `/`**：`27 // 2 = 13`，`27 / 2 = 13.5`。卷积只走整数步，零头丢掉。

**括号不能省**：`H + 2*p - k // s` 会先算 `k // s`，结果完全错。

### 6 组实测核对（全部 OK）

```text
in=  5 k=3 p=0 s=1 | 手算=  3 实际=  3
in=  5 k=3 p=1 s=1 | 手算=  5 实际=  5
in=  5 k=3 p=2 s=1 | 手算=  7 实际=  7     ← 唯一「变大」的情况
in= 28 k=3 p=1 s=2 | 手算= 14 实际= 14
in=224 k=7 p=3 s=2 | 手算=112 实际=112     ← ResNet 第一层
in= 11 k=3 p=0 s=4 | 手算=  3 实际=  3     ← 不整除，靠 // 丢尾
```

### 两条必背口诀

```text
k=3, padding=1, stride=1  →  尺寸不变   （28 → 28）
k=3, padding=1, stride=2  →  尺寸减半   （28 → 14）
```

这是 CNN 设计里最常用的两个组合：**堆层不改尺寸用第一个，降采样用第二个。**

### 第三招：padding = (kernel - 1) // 2

```text
3x3 → pad 1     5x5 → pad 2     7x7 → pad 3
```

**VGG 全是 3×3 + pad 1**，就是这个道理。

## 五、参数量公式（今天第一重点）

```text
Conv2d 参数量 = kernel_h * kernel_w * Cin * Cout + Cout
```

拆成四步理解：

```text
k * k         核的面积（3×3 = 9）
* Cin         深度上要看几层（每个输出通道都要看全部输入通道）
* Cout        要几套这样的核（= 输出通道数）
+ Cout        bias，每个输出通道一个
```

### 5 组实测核对（全部 OK）

```text
Conv2d(1 -> 16, k=3)     手算=  160   实际=  160
Conv2d(1 -> 64, k=3)     手算=  640   实际=  640
Conv2d(3 -> 64, k=3)     手算= 1792   实际= 1792
Conv2d(16-> 32, k=3)     手算= 4640   实际= 4640
Conv2d(3 -> 64, k=7, s=2) 手算=9472   实际= 9472
```

**三个必背（面试常问）：**

```text
Conv2d(1, 64, 3)     = 640       灰度图第一层
Conv2d(3, 64, 3)     = 1792      RGB 第一层
Conv2d(3, 64, 7, 2)  = 9472      ResNet 的 stem
```

### 为什么 `Conv2d(3,64,3)` 是 1792 不是 576

```text
3*3*64 = 576        只算了「一套核 × 64 个通道」
但输入是 3 通道      每个位置要把 3 个通道的值全部加完
3*3*3*64 = 1728     所以 ×3
+64 = 1792
```

**记忆点：`k*k` 是平面大小，`Cin` 是「深度上叠加几个通道」，`Cout` 是「要几套」。**

### 关键结论：参数量与图片大小无关

`Conv2d(3, 64, 3)` 处理 224×224 和 1024×1024，**参数永远是 1792。**

公式里没有 `H` 和 `W` 这两个变量 —— 这就是 CNN 能处理高清图的根本原因。

### 顺带两个「不影响参数量」的量

| 参数 | 影响什么 | 影响参数量吗 |
|---|---|---|
| `padding` | 输出尺寸 | ❌ |
| `stride` | 输出尺寸 | ❌ |
| `kernel_size` | 输出尺寸 + 参数量 | ✅ |
| `Cin` / `Cout` | 通道数 + 参数量 | ✅ |

**`stride` 改的是「核滑几步」，不改「核里有多少个数」。**

## 六、FLOPs（今天第二重点）

### 先把三个概念分清

| 概念 | 是什么 | 有实体 | 单位 |
|---|---|---|---|
| **卷积核** | 一组具体的数 | ✅ 是张量 | 个数 |
| **参数量** | 所有要存的数加起来 | ✅ 整数 | 个 |
| **FLOPs** | 前向一次要做多少次浮点运算 | ❌ 只是个计数 | 次 |

**卷积核是「东西」，FLOPs 是「动作次数」。**

### 还有一个命名陷阱

```text
FLOPs（小写 s）  = 运算总数          ← 模型要算多少
FLOPS（大写 S）  = 每秒运算次数      ← 硬件算多快
```

显卡写 `RTX 3050 约 9 TFLOPS`（速度），模型写 `ResNet-50 约 4.1 GFLOPs`（总量）。
**估算时间：4.1 G ÷ 9 T ≈ 0.46 毫秒（理论下限，实际打 3~5 折）。**

### 公式

```text
MACs = out_h * out_w * Cout * kernel_h * kernel_w * Cin
FLOPs = 2 * MACs          （1 次乘加 = 1 次乘 + 1 次加 = 2 FLOPs）
```

**怎么想出来的**：输出里每个数字要做 `k*k*Cin` 次乘加，输出一共 `out_h*out_w*Cout` 个数字，两层相乘。

### 实例手算：224×224×3 → 64，k=3，pad=1，s=1

```text
第一步 输出尺寸:  (224 + 2 - 3)//1 + 1 = 224      → 224 × 224 × 64
第二步 一位运算:  3 * 3 * 3 = 27 次乘加
第三步 位置总数:  64 * 224 * 224 = 64 * 50,176 = 3,211,264

MACs  = 3,211,264 * 27 = 86,704,128
FLOPs = 2 * 86,704,128 = 173,408,256    约 173.41 M
参数量 = 3*3*3*64 + 64 = 1792
```

### 这里藏着一个漂亮的数字

```text
86,704,128 ÷ 1,728（纯 weight 数） = 50,176
```

**每个权重被复用了 50,176 次** —— 正好等于 224×224 个位置各用一次。

**这就是「权重共享」的量化表达：9 个数，在 5 万个位置上反复使用。**

### 参数量和 FLOPs 差 4.8 万倍

```text
1792 个参数  vs  8670 万次乘加
```

**这两个完全不是一个维度的东西**：一个衡量存储，一个衡量工作量。看到「CNN 很省参数」和「CNN 很费算力」两个说法同时成立，就是因为这个。

### 换算成时间感受

```text
0.173 GFLOPs ÷ 9000 GFLOPS ≈ 0.019 毫秒     理论
实际因为访存/调度，慢 5~10 倍，但仍在一毫秒内
```

**所以 CNN 看着「算得凶」，实测每轮训练只要 11 秒。**

### 一个诚实的细节：bias 的加法

严格算每个输出位置要加 1 次 bias：`3,211,264` 次加法。但只占 8670 万的 3.7%，**工程上一般不计入**。

**看到别人给的 FLOPs 和你差一点点，多半是 bias 算不算的差别。**

## 七、`nn.Conv2d` 使用细节（几条容易踩的）

### 1. 里面的东西：weight 和 bias

实测 `Conv2d(1, 64, 3)`：

```text
print(conv)  →  Conv2d(1, 64, kernel_size=(3, 3), stride=(1, 1))
weight 形状: torch.Size([64, 1, 3, 3])   → 576 个数
bias   形状: torch.Size([64])            → 64 个数
总参数: 640
```

**weight 的形状是 `(Cout, Cin, kH, kW)`，不是 `(kH, kW)`。**

**64 通道 = 里面装着 64 个不同的 3×3 核。** 初始化是随机的，训练后它们会分工成检测竖边、横边、斜边、斑点等不同模式。

### 2. 默认 padding=0，尺寸会掉 2

```python
nn.Conv2d(1, 64, 3)              # 28 → 26   ← 默认 padding=0
nn.Conv2d(1, 64, 3, padding=1)   # 28 → 28   ← 才是"尺寸不变"
```

**很多人以为「默认不改变尺寸」，其实默认是掉 2。**

### 3. 输入必须四维 (N, C, H, W)

```python
x = torch.tensor([[...5行...]])       # (5, 5)   25 个数
x = x.view(1, 1, 5, 5)                # (1,1,5,5) 还是 25 个数
```

**`view(1,1,5,5)` 的作用**：补上 batch 维和 channel 维。

实测三个数字说明了它的本质：

```text
view 前: torch.Size([5, 5])      numel = 25
view 后: torch.Size([1, 1, 5, 5]) numel = 25
同一块内存: True
```

**一个数都没变，只是「解读方式」变了。** 可以理解为同一张 25 格的纸，重新贴了标签「第 1 批、第 1 通道、5×5」。

### 4. 一个隐蔽的坑：三维输入也能跑

实测：

```python
conv(x5.view(1,5,5))       # 不报错！
```

新版权重允许**「无 batch 的 3 维输入」**，会被理解成 `(C=1, H=5, W=5)`，输出 `(1,3,3)` —— **比正确结果少了 batch 维**。

**单张图调试时数字一样，换成 batch=64 就会报错。所以规矩是：一律写四维。**

喂真正的二维 `(5,5)` 才报错：

```text
RuntimeError: Expected 3D (unbatched) or 4D (batched) input to conv2d,
but got input of size: [5, 5]
```

### 5. 手动指定卷积核：`weight.data`

任务 1 里这两行：

```python
conv = nn.Conv2d(1, 1, 3, bias=False)     # 建层，weight 是随机的
conv.weight.data = k                       # 把随机值换成我们的核
```

**为什么必须 `bias=False`**：不加会多一个随机 bias。实测那个随机 bias 是 `-0.3092`，于是输出全变成 `-6.3092`，跟手算的 -6 对不上。

**为什么必须 `.data`**：`conv.weight` 是 `Parameter`（`requires_grad=True`），直接赋值会报错：

```text
TypeError: cannot assign 'torch.FloatTensor' as parameter 'weight'
(torch.nn.Parameter or None expected)
```

`.data` 是同一块内存的普通视图（实测 `data_ptr` 相同），能绕过这层检查。

**更规范的写法：**

```python
with torch.no_grad():
    conv.weight.copy_(k)
```

**注意**：这只是教学/固定滤波器（Sobel、高斯核）用的手段。**正常训练绝不这么写**，权重是让损失学出来的。

## 八、CNN vs MLP：今天最有说服力的一组实测

### 模型结构

```python
class CNN(nn.Module):
    def __init__(self):
        super().__init__()
        self.f1   = nn.Conv2d(1, 16, 3, padding=1)
        self.f2   = nn.Conv2d(16, 32, 3, padding=1)
        self.pool = nn.MaxPool2d(2)
        self.fc   = nn.Linear(32*7*7, 10)
        self.relu = nn.ReLU()

    def forward(self, x):
        x = self.pool(self.relu(self.f1(x)))     # (N,1,28,28) → (N,16,14,14)
        x = self.pool(self.relu(self.f2(x)))     #             → (N,32,7,7)
        return self.fc(x.flatten(start_dim=1))
```

### 各层 shape（实测）

```text
输入       : (64, 1, 28, 28)
conv1+relu : (64, 16, 28, 28)
pool1      : (64, 16, 14, 14)
conv2+relu : (64, 32, 14, 14)
pool2      : (64, 32, 7, 7)
flatten    : (64, 1568)        ← 32 * 7 * 7
fc         : (64, 10)
```

**两层 pool 只改尺寸不改通道数**：28→14→7，通道 16→32。

**1568 = 通道 × 高 × 宽**，这就是 Linear 的输入维度。以后写任何 CNN 都这样推。

### 参数量三行加出来

```text
conv1: 3*3*1*16 + 16   = 160
conv2: 3*3*16*32 + 32  = 4640
fc:    32*7*7*10 + 10  = 15690
合计: 20490
```

**注意 fc 占了 15690 / 20490 = 76%。** 卷积层加起来只有 4800 个参数 —— **大部分参数其实在最后那个全连接层。**

这也是为什么后来的网络（ResNet）用全局平均池化替掉大 fc：**它太吃参数，而且容易过拟合。**

### 三个结论

**① 参数少 5 倍，效果更好**
20490 vs 101770，第 3 轮 98.58% 超过 MLP 跑满 5 轮的 97.57%。

**② 但耗时略长**
每轮 11.3s vs MLP 11s。原因在 FLOPs：

```text
MLP 每张图 MACs = 784*128 + 128*10 = 101,632      约 0.10 M
CNN 每张图 MACs = 112,896 + 903,168 + 15,680 = 1,031,744   约 1.03 M
CNN 是 MLP 的 10 倍
```

**参数省了 5 倍，算力费了 10 倍 —— 这就是「卷积用计算换参数」的真实含义。**

**③ MNIST 太简单，CNN 优势不明显**
只高 1 个百分点，而且第 3 轮就饱和了。**差距真正拉开要到 CIFAR-10、猫狗、检测任务**，那时 MLP 根本训不动。

## 九、今天学到的一个写法：表驱动核对

任务 2、3 的代码是同一个骨架：

```python
cfgs = [(5,3,0,1), (5,3,1,1), ...]        # 1) 参数表

for a, b, c, d in cfgs:                    # 2) 逐行解包
    manual = 公式(...)                     # 3) 手算
    actual = 实测(...)                     # 4) 实测
    flag = "OK" if manual == actual else "WRONG"
    print(f"... 手算={manual:3d} 实际={actual:3d} | {flag}")
```

**为什么这么写：**

1. 加一组实验只加一行，不复制代码
2. 顺序和任务卡表格一一对应，答案不会错位
3. **这是后面所有实验的标准写法**：试不同 batch、lr、核大小、层数，全用这招

### 两个格式细节

```python
{H:3d}        # 占 3 字符宽、右对齐、整数
{H:6d}        # 数字有四位数（如 9472）时要用 6d，否则列会歪
```

**列对齐了，一眼就能看出哪一行不一样。** 六组以上数据，这个投资很值。

### 两个易错点

- `for H, p, k, s` 顺序错了不会报错，只会算错 —— **顺序必须和元组一致**
- `torch.randn(1,1,H,H)` 只是「符合形状的填充物」，**值不重要，我们只看 shape**

### 任务 6 的报错原文（已实测，可直接背）

```text
RuntimeError: mat1 and mat2 shapes cannot be multiplied (64x1568 and 784x10)
```

**读法：**

```text
64x1568   ← 实际喂进去的：64 张图，每张摊平后 1568 个数

1568 ≠ 784 → 乘不起来
```

### 我自己的 4 道思考题答案（已整理）

**第 1 题（参数量差距）**

```text
MLP 224 彩色: 150,528*128 + 128 = 19,267,712   约 1927 万
Conv2d(3,64,3):                    1,792
差 10,752 倍

1080p: 6,220,800*128 + 128 = 796,262,528       约 7.96 亿
差 44.4 万倍，光第一层就要 3 GB 显存
```

**第 2 题（局部连接 / 权重共享）**

- 局部连接解决**参数量爆炸**：每个输出只连 3×3×3 = 27 个输入，而不是全部 15 万个
- 权重共享解决**平移等变 + 参数与尺寸无关**：同一个核在位置 A 和 A+1 用同一组数，所以响应值完全相同，图像平移后特征图也整体平移，数值不变
- **「7 挪一格还是 7」的原因**：MLP 每个像素配一套独立权重，平移一像素整套对应关系就乱；CNN 是同一组权重扫过去，图案没变响应就不变

**第 3 题（640 参数 vs 8670 万次运算）**

划算。核心数字：

```text
86,704,128 ÷ 1,728 = 50,176       每个权重被复用 50,176 次
```

三个理由：算力便宜（0.02 毫秒理论）、存储和泛化贵、参数少部署有优势（CNN 权重 82 KB vs MLP 409 KB）。**只在算力极紧张的低端芯片或极小图上才不划算。**

**第 4 题（CNN 到底强在哪）**

1. **归纳偏置**：局部性、平移等变、层级组合是「装在结构里的先验」，所以小数据也能学 —— **这是 MVTec 那种每类几十张图的场景 CNN 能跑、MLP 会过拟合的根本原因**
2. **参数效率**：少 5 倍，泛化更好
3. **可扩展性**：224×224 能跑，1024×1024 也能跑（参数不变）

**必须用 CNN 的场景**：分辨率 > 100×100、需要在图上滑窗找东西（缺陷/行人/病灶）、数据量小但要泛化、需要空间信息（定位/分割）、语音时序（一维卷积）。

**MLP 够用的场景**：28×28 小图（MNIST 这种）、表格数据、特征已工程化。

**我自己的实验就是证明**：MNIST 太简单，CNN 只赢 1 个点；差距要到 CIFAR-10 / 猫狗才拉开。

## 十二、明日（day6）

主题：**感受野** —— 为什么「3 个 3×3 卷积」等于「1 个 7×7 卷积」。

脚本：`stage3_pytorch/day6_cnn_receptive_field.py`

今天预埋的两个数（明天直接用）：

```text
1 个 7×7 卷积:  7*7*Cin*Cout + Cout          参数 k^2
3 个 3×3 卷积:  3 * 3*3*Cin*Cout + Cout      参数 3k^2  → 少 44%
感受野:         1 层 3×3 → 3； 2 层 → 5； 3 层 → 7
```

**用 3 层 3×3 换 1 层 7×7：感受野相同，参数少 44%，中间多两次非线性。** 这是 VGG 的核心思想。
